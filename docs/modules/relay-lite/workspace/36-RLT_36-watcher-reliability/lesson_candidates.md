### 候选-004 · 常驻监控的生命周期须绑定真实进程而非模型回合

触发场景：监控 agent 的模型回合可能 idle、done 或暂停，但已授权任务仍依赖持续观察。 · 建议分类：行为流程 · 来源：findings「原始现场」；review.plan PR36-01；E-007 scene-A/scene-B
疑似重复：无
- 现象：原 watcher 在通知后的短时 UI 状态未满足时退出循环，模型回合结束也会被误当作监控已失效，使任务等待外部唤醒。
- 反思：把模型 agent 的回合状态、通知结果和独立观察程序的存活混为同一个生命周期，缺少对真实子进程句柄的持续核验。
- 建议后续动作：将常驻观察置于独立普通终端的固定进程；记录并巡检精确 PID/退出码，模型回合只负责一次启动确认。演练须覆盖模型回合结束后同一进程跨观察节拍仍存活，以及监控进程停止后的降级路径。
状态：待裁决

### 候选-005 · 通知提交确认不得替代接收方消费或任务核收

触发场景：向 busy、审批中或状态未变化的 agent 发送监控通知。 · 建议分类：行为流程 · 来源：review.md RL36-M2；review.plan PR36-01；E-007 scene-A
疑似重复：无
- 现象：曾以接收方的 `working` 或 `state_change_seq` 推进作为通知已消费的条件；在目标忙碌且提交实际成功时会误判失败并停止监控。
- 反思：提交动作、接收方实际消费和任务完成是三个不同事实，后两者不能从一次提交或 UI 状态变化反推。
- 建议后续动作：通知层只记录一次提交的已确认/未知事实；未知不盲重发并继续观察。任务放行只由精确 durable signal、原始报告及适用复核核收，演练分别证明 busy 提交与无通知核收。
状态：待裁决

### 候选-006 · 监控缺席时由 owner 执行精确且有界的只读结果等待

触发场景：watcher 暂停、退出或通知无法依赖，而主编排仍须等待当前已派发任务的结果。 · 建议分类：行为流程 · 来源：review.md RL36-M4/M5；review.plan PR36-03；E-007 orch-report.md
疑似重复：无
- 现象：没有 watcher 时，编排容易因一次 PENDING、idle/done 或 READY 提前结束、无限空等，或误接收旧轮/错任务 signal。
- 反思：等待路径未把结果身份、等待预算、PENDING 后续动作与 READY 后 owner 核验固定为一个完整合同。
- 建议后续动作：只读等待必须匹配任务、phase、agent、batch、path、review_round、remediation_count；PENDING 在预算内继续，预算耗尽或 worker 明确失败/停止无 signal 时保留阻塞。READY 后仍核原报告、signal/hash、字段和实际停止状态，且不把 READY 当 PASS。
状态：待裁决
